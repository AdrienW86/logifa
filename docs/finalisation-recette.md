Branche : `develop/logifa`. Ce rapport complète les rapports historiques 3A, 3A.1, 3A.2, UX et TypeScript ; leurs résultats correspondent à leurs versions respectives. Aucune migration distante, aucun push, aucun e-mail réel, aucune requête OpenAI payante. Références locales : `e59a2f1` (première couche de persistance), `c57aa8a` (consolidation et intégrité SQL), `da5b991` (interfaces, parcours serveur, PDF contrôlés, agent et Resend multi-comptes avec tests). `master` reste sur `f35906f`. Les fichiers temporaires, `.env.local`, secrets et sorties de build restent hors Git.

## Livraison

- Les trois migrations corrigées sont consolidées dans le commit SQL `c57aa8a`. Il n'existe plus de quatrième migration de workspace. `schema_version: 4` dans le RPC health désigne la révision du modèle, pas le nombre de migrations.
- Chaque nouveau client appartient à un `issuer_profiles`. Des fiches homonymes dans deux carnets restent distinctes, même lorsque leurs émetteurs partagent une entité juridique. FKs composites et triggers empêchent les rattachements croisés : clients, chantiers, devis, factures et mouvements. Les anciennes fiches non attribuées restent conservées avec rattachement NULL et type `unknown` ; aucune attribution, fusion ou requalification supposée.
- Les neuf profils locaux sont importables explicitement, sans fusion des identifiants historiques dupliqués ni rattachement juridique automatique. Entités fiscales et profils commerciaux sont séparés ; les séries appartiennent à l'entité juridique.
- Accueil et sections `/gestion/*` : entreprises, clients, devis, factures, paiements, documents, paramètres. Les indicateurs proviennent des documents et paiements serveur ; les avoirs diminuent le facturé, les remboursements diminuent les encaissements, les déductions d'acompte ne constituent pas de nouveaux encaissements.
- Le même éditeur manuel reçoit le carnet client, les suggestions, les adresses de chantier, la sauvegarde/réouverture serveur, la duplication et les parcours financiers. Sauvegardes locales par administrateur, émetteur et type ; contrôle optimiste des révisions serveur. Le document émis est verrouillé et ses instantanés restent immuables. L'ajout IA passe par la revue du même formulaire.
- Acompte calculé en montant TTC ou pourcentage à partir du devis réel, avec TVA source. Les arrondis non représentables exactement sont refusés pour revue, sans ajustement silencieux. Avoir après finale sur acompte déjà déduit : opération automatique bloquée, régularisation comptable/fiscale coordonnée nécessaire. Avoir documenté sur finale disponible, sans modifier les originaux.
- Suppression limitée au devis brouillon jamais émis, numéroté, envoyé, lié à une facture, paiement, signature ou fichier. Vérification transactionnelle et événement d'audit conservé ; les clients et historiques ne sont pas supprimés.
- Import d'originaux historiques, versions signées et justificatifs privés ; aucune mention historique « payé » ne crée un paiement. Original et variante acquittée sont des objets séparés. Les empreintes SHA-256 sont vérifiées à la lecture. Après remboursement, une ancienne variante acquittée reste conservée mais sa délivrance comme version actuellement acquittée est refusée.
- Les générateurs classiques `utils/generatePdf.js` et `utils/generateFacture.js`, leurs ressources et leurs rendus de référence sont inchangés. Les nouveaux `managedQuote.ts` et `managedInvoice.ts` utilisent les montants, TVA, mentions et déductions serveur et une annexe explicite. Ils ne remplacent pas rétroactivement les originaux. Les actions PDF classiques sont bloquées pour un document serveur émis afin de ne pas produire une facture fiscale incorrecte.
- Chaque émetteur garde son propre compte Resend. Clé API AES-256-GCM avec nonce aléatoire et authentification liée à l'émetteur ; clés dérivées distinctes pour chiffrement et signature des aperçus. Paramètres privés serveur, rotation et vérification du domaine par le compte correspondant, aperçu signé 15 minutes, confirmation humaine, idempotence et journal `sending/sent/failed/unknown`. Aucun secret renvoyé dans les réponses, l'historique ou les erreurs. « sent » signifie accepté par le fournisseur ; aucune preuve de livraison ni transmission réglementaire n'est inventée.
- Adaptateur OpenAI Responses à sortie structurée, désactivé par défaut avec double activation explicite. Contexte minimal de l'émetteur, client/formulaire et catalogue ; pas de clé ou coordonnées bancaires transmis. Validation à l'exécution, preuves des mesures/prix, informations manquantes explicites, conservation des lignes manuelles, aucune capacité d'émission/paiement/envoi. Limitation locale 10 demandes/heure par administrateur, délai 45 secondes, `store: false`.
- TypeScript strict pour le code applicatif migré. Les deux moteurs PDF historiques restent volontairement en JavaScript ; les scripts de recette et de maintenance restent des scripts Node/PowerShell. Aucun `any` nécessaire pour contourner les contrats.

## Limites avant production

La recette locale **ne valide pas** la signature/expiration de véritables JWT Clerk, le rejet HTTP par Supabase d'un mauvais issuer, les vrais grants gérés par Supabase, les accès Storage HTTP, le domaine/DNS Resend, la délivrance d'e-mails ni une réponse OpenAI réelle. Les claims PostgreSQL et fournisseurs fictifs sont identifiés comme simulations. Les variables de persistance/agent/mail n'étant pas configurées localement, aucune connexion réelle à ces services n'est annoncée comme validée.

Les lectures de listes sont plafonnées à 500 et signalent explicitement les données partielles ; les indicateurs ne doivent pas être interprétés comme un grand livre exhaustif dans ce cas. Le verrou administrateur global sérialise les opérations financières : bon compromis pour un administrateur unique, à mesurer si la charge augmente. La limitation OpenAI est en mémoire du processus, pas distribuée.

Storage et PostgreSQL ne partagent pas une transaction distribuée. Un upload réussi suivi d'un refus SQL peut laisser un objet privé non enregistré ; ne jamais l'écraser. Les retries vérifient les octets/SHA et les imports ont une clé stable. Un rapprochement opérationnel des objets orphelins reste nécessaire. Un échec de journalisation après réponse Resend peut laisser `sending` : rapprocher le tableau de bord avant tout nouvel envoi, aucune relance automatique.

Les historiques sans rattachement ne sont pas visibles dans un carnet attribué. Leur affectation requiert une décision explicite et documentée, après inventaire ; aucun script de reprise automatique n'est livré. Les mentions fiscales, régime TVA, entités/SIRET, échéances, assurances et coordonnées bancaires doivent être qualifiés par l'administrateur. Le moteur classique facture conserve son ancien comportement TVA zéro ; utiliser le parcours serveur adapté pour les nouveaux documents fiscaux.

Ni plateforme agréée de facturation électronique, ni export Factur-X certifié, ni signature qualifiée ne sont intégrés. L'envoi Resend reste une communication de PDF, pas une transmission réglementaire. Le logiciel ne prétend pas satisfaire seul toutes les obligations fiscales. Référence : [mentions et calendrier français](https://www.economie.gouv.fr/entreprises/gerer-son-entreprise-au-quotidien/gerer-sa-comptabilite-et-ses-demarches/mentions-obligatoires-dune-facture-tout-savoir).

Avant production : obtenir l'accord pour une recette Supabase isolée, qualifier les données et mentions, tester les vrais jetons/Storage et les restaurations, puis décider séparément toute application au projet principal. Aucun coût ou création d'environnement n'a été engagé.
